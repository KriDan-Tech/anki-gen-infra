# Правило документации dev-anki-gen

Когда меняются продуктовые требования, поведение, межсервисные контракты, жизненный цикл данных/денег, тарифы или эксплуатационные зависимости, обновляйте соответствующие страницы `docs/` в том же наборе изменений, что и источник изменения. Это правило относится к общим polyrepo docs, а не к workspace-level AGENTS.md.

Для каждого сервисного описания сохраняйте раздельно: наблюдаемая реализация (с точными относительными путями файлов, датой осмотра и версиями только при проверке manifest), утверждённая целевая спецификация и gaps/unknowns. Ссылки на узкие API/операционные документы предпочтительнее копирования длинных endpoint/config inventories. Статическое чтение исходников не доказывает runtime или deployed состояние; явно указывайте эту границу.

Если изменение не влияет на требования/архитектуру/эксплуатацию, в задаче или review прямо отметьте «документация не затронута» и краткую причину. При новом влиянии обновляйте дату и источники, не переписывайте observed implementation под желаемое поведение.

Канонические ссылки из компонентных README должны вести на опубликованное зеркало `infra/docs/project/` в `main`, чтобы работать в standalone clone; в самом polyrepo можно пользоваться общим `docs/`. Поддерживайте зеркало с каноническими файлами в том же publication change, проверяйте repository URL по фактическому remote, не изобретайте адреса. Не заявляйте, что unpublished shared docs уже доступны в standalone clone. Не включайте секреты или личные данные.
